The Arachnid deterministic-deployment proxy treats *everything* after the first 32 bytes (salt) as literal init code to execute via `CREATE2` — it does not parse it as "function calldata with an ignorable trailing suffix" the way a normal contract call does. ## Maintenance — the sentinel had silently stopped running

- **2026-07-28**: **Kokosh is a wallet-hygiene sentinel that had quietly stopped reporting, and nothing surfaced it.** Noticed while reviewing project state, not from any alert — which is itself the point. `docs/sentinel-cron.log` showed today's cycle logging `sleeping 243s of jitter before running` and then **nothing at all**, while `docs/sentinel-state.json` still carried `lastRunAt: 2026-07-23`. Silence in the log was indistinguishable from a healthy stand-down.
  - **Root cause (the real one): the incremental scan could never survive a gap.** `scanNewApprovals` issued a single `eth_getLogs` spanning `lastScannedBlock+1 → latest`. Base's public RPC rejects any range over 10,000 blocks (`-32614`, "eth_getLogs is limited to a 10,000 range"), and Base produces ~43,000 blocks/day — so **any** run more than roughly 5.5 hours after the previous one was guaranteed to fail. The very first run (2026-07-23) only passed because the state file had just been seeded to the then-current tip and the run followed immediately. The design was never actually exercised against a realistic gap.
  - **Why it was invisible: `set -e` plus command substitution.** `sentinel-cron.sh` did `output="$(cd agent && node scripts/sentinel-run.mjs 2>&1)"`. On a non-zero exit the shell aborted *at that line* — before `echo "$output"` ever ran — so the captured error was discarded and the log just stopped mid-cycle. The wrapper now runs the scan under `set +e`, keeps the exit status, always echoes the output, and logs an explicit `sentinel-run FAILED (exit N) — output above, state not advanced`. It also logs `jitter complete, starting scan` after the sleep, so a cycle killed mid-jitter (a WSL2 session ending, say) is distinguishable from one that reached the scan and then broke, and `run finished cleanly` on success — silence is no longer ambiguous in either direction.
  - **Chunking, then a second failure underneath it.** Split the range into windows of `MAX_LOG_RANGE` (default 9,500, env-tunable). That got past `-32614` and straight into `-32016 "over rate limit"` — 25 windows × 2 event signatures, fired via `Promise.all`, is simply too dense for `mainnet.base.org`. Fixed by making the two chunked walks **sequential** rather than concurrent, pacing windows with `WINDOW_DELAY_MS` (default 250ms), and wrapping every call in `withRateLimitRetry` (5 attempts, 2s doubling backoff, only on rate-limit errors — anything else still throws immediately). The same wrapper had to go around the per-pair `allowance` reads too, which hit the limit next once the log walk stopped being the bottleneck.
  - **Added `DRY_RUN=1`** — runs the entire scan, including the chunked walk that actually broke, but submits no attestation and does not advance the state file. Without it there was no way to verify a fix against real mainnet data without on-chain side effects, which is why the original bug went unexercised.
  - **Verified end to end, against mainnet, not simulated**: dry run walked 232,255 blocks in 25 windows, hit the rate limit three times, backed off, recovered, and completed with `no new findings — standing down` (exit 0). Failure path re-tested deliberately by forcing `MAX_LOG_RANGE=999999` — the `-32614` error now lands in the log followed by the `FAILED` marker, exit 1. Then a real (non-dry) run advanced the state: `lastScannedBlock` 49009689 → 49241986, `lastRunAt` 2026-07-28.
  - **Side benefit**: that real run is an independent confirmation of the same day's Ledger block session — scanning every approval event across those 232k blocks and reading each pair's live allowance found **zero** still-live approvals, matching what that session claimed after its cleanup pass.
